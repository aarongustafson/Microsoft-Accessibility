## [0.58] - 2026-05-24

- **Goal**: Stop `Remove-StaleVibeShieldAptSource` from throwing `IndexOutOfRangeException` on real corrupt WSL hosts so Bug 528576's `[Pre]` cleanup actually reaches the removal step.
- **Why**: Real-world WSL validation of PR #37367 revealed `Invoke-DpkgQueryNative` can return `{ExitCode=0; Output=@(); StdErr=''}` for the user's unowned `microsoft-dotnet.list` -- an anomalous shape (exit 0 normally means owned) the helper had never observed in fixtures. Line 155's `@($dq.Output)[0]` then threw under StrictMode, the outer try/catch surfaced "Index was outside the bounds of the array.", and the legacy file stayed on disk -- leaving the user stuck in exactly the apt-collision state Bug 528576 is meant to repair. The content-signature gate already proved the file is the ef34 invariant before dpkg is consulted, so a degenerate dpkg response cannot indicate a real package owner; the safest behavior is to fall through to removal, not abort.
- **What**:
  - StrictMode-safe access in the `dpkg-query ExitCode=0` branch: `$firstLine = @($dq.Output) | Select-Object -First 1` plus restructured `return` so `dpkg-owned` only fires when an owner line is actually parsable.
  - New fall-through path: exit 0 with empty/unparseable stdout now emits a `Write-Verbose` (scored 5.0/5 on `output/error-messaging.md` rubric -- names the function, command, exit code, the captured first stdout line truncated to 80 chars or `<empty>`, the decision, and the manual verify command `dpkg-query -S <path>`) and falls through to removal.
  - 7 new Pester tests in 2 new contexts ("Bug 528576 crash site" and "unparsable output") that mock `Invoke-DpkgQueryNative` with the exact anomalous shape from the user's stack trace; both confirm RED -> GREEN and assert `sudo rm` was invoked. Suite count rises 38 -> 45; all 5 PackageSupport suites stay green (45/43/43/19/71). Audited every other `@(...)[0]` site in `.vibeshield/PackageSupport/` -- all guarded.
  - Council review: R4 (Opus 4.7 + GPT-5.5) APPROVE WITH NITS -> 4 nits applied (docstring updated for both fall-through paths, Verbose includes truncated payload + verify command, test scope hazard documented) -> R5 (same reviewers) APPROVE (Ship).

## [0.56] - 2026-05-19
- **Goal**: Close ADO bug [528576](https://dev.azure.com/oneCELA/CELA%20Engineering/_workitems/edit/528576/) -- Phase 6 `.NET` install fails on WSL/Linux re-install when the legacy Path B apt-source file (`microsoft-dotnet.list`, written by commit `ef34b03` before the Helper B migration) is still present alongside the Path A file (`microsoft-prod.list`) that `Sync-MicrosoftAptSource` now manages, because the two files declare the same `URI + Suite` with different `Signed-By` keys and `apt-get update` aborts before any `Sync-MicrosoftAptSource` reconciliation runs.
- **Why**: The Phase 6 (`0.53`) migration to `Sync-MicrosoftAptSource` was correct for first-install but blind to the pre-existing artifact left by the prior installer path. The collision invariant -- *same URI, same Suite, different Signed-By* -- causes `apt-get update` to exit non-zero with `Conflicting values set for option Signed-By regarding source ...`, which the orchestrator currently surfaces as an opaque "step failed" without identifying the apt-source collision class or the legacy file as the cause. The Sync helper's own conflict detection runs *after* its `apt-get update` (Step 4), so the user is told to re-run after Sync has already exited cleanly on a system where no further work succeeds. The collision class is also self-induced -- legacy artifacts written by the *same* tool a prior commit shipped -- so the remediation must be conservative auto-cleanup of the known signature plus a defense-in-depth preflight that detects general collisions before any apt operation. The collision must be caught and resolved at the orchestrator boundary, *before* the dotnet step runs, with errors that name the operation, the reason, the file, and the recovery commands; the rubric in `output/error-messaging.md` is the gate.
- **What**:
  - **New `Private/Test-MicrosoftAptSourceConflict.ps1`** (139 LOC) -- reusable conflict scanner. Calls `Get-AptSourceRecord`, filters Microsoft-relevant entries, groups by `URI|Suite`, and throws a single typed `[System.InvalidOperationException]` if any group has more than one distinct `Signed-By` value. Throw message lists each conflicting record with its full `FilePath` plus owner label (`unowned -- handwritten`) and ends with the user-actionable line: "Remove or disable one of the duplicates and re-run." Replaces the inline group/throw block formerly at Sync Step 4 (which is now a 3-line delegate). Called by `Install-VibeShieldDotNet` preflight (Phase 'PreApt') and by Sync at the same Phase 4 and a new post-install Phase 'PostInstall' (Step 7d, see below).
  - **New `Private/Remove-StaleVibeShieldAptSource.ps1`** (210 LOC) -- one-time legacy migration. Auto-removes *only* the known ef34 signature (`microsoft-dotnet.list` whose `Signed-By` keyring path matches the regex `/etc/apt/keyrings/microsoft.gpg` anywhere in the options string, irrespective of `arch=` / `Suite` option order). Defense-in-depth gate via `Invoke-DpkgQueryNative -S` *before* `rm`: if dpkg owns the file, the helper returns `Action='no-op'; Reason='dpkg-owned'` and refuses to delete (because that means a package -- not legacy installer drift -- put it there). Returns one of 8 typed (Action, Reason) shapes (`'removed'`, `'no-op'`/`'absent'|'mismatched-signature'|'dpkg-owned'|'unsupported-platform'`, `'failed'`/`'dpkg-query-error'|'rm-failed'`, `'skipped'`/`'after-retirement-date'`). Takes `-SourcesDirectory` and `-RetirementDate='2026-06-30'` parameters for testability and operational sunset. `-ForceLinux` test-only switch enables cross-platform Pester (documented in-source).
  - **New `Installers/Install-DotNetViaApt.ps1`** (212 LOC) -- extracted from the 144-line apt branch of `Install-VibeShieldDotNet.ps1` into a private function. The extraction turns the preflight-before-`apt-get update` ordering invariant from a `-Skip:(-not $IsLinux)` integration test into a real cross-platform unit test (Opus R2 finding Maj-3). Preserves all 10 `return $result` sites and the early-return contract documented inline (`Action='failed'` always short-circuits the caller; `Action='skipped'` short-circuits only when `Message` is non-empty, covering WhatIf and contract-drift cases; success leaves `Action='skipped'` with empty `Message` and the caller falls through to post-install verification).
  - **Orchestrator wired** -- `Installers/Install-PackageSupport.ps1` runs `Remove-StaleVibeShieldAptSource` as a `[Pre]` pseudo-step *before* the `$stepDefinitions` loop, so the legacy artifact is gone before *any* installer runs `apt-get update`. The synthesized failed-step `Message` preserves the helper's `Reason`, `FilePath`, and `Detail` so the surface message lifts from rubric 2.2 to 5.0 (was a bare "Legacy apt-source cleanup: failed"; now reads `'Legacy apt-source cleanup failed (dpkg-query-error) for /etc/apt/sources.list.d/microsoft-dotnet.list: dpkg-query: ... try sudo dpkg --configure -a and sudo apt-get update and re-run. The legacy file ... was NOT removed.'`).
  - **`.NET` Linux preflight** -- `Install-DotNetViaApt` invokes `Test-MicrosoftAptSourceConflict -Phase 'PreApt'` *before* the first `apt-get update` call. Defense-in-depth for any other non-legacy collision the orchestrator's one-time cleanup cannot anticipate.
  - **Sync gets Step 7d post-install rescan** -- after `dpkg -i packages-microsoft-prod.deb` writes Path A and before `apt-get install -f -y` runs (Step 7e, renamed from 7d), Sync rescans with `Test-MicrosoftAptSourceConflict -Phase 'PostInstall'`. Catches the race where the user's machine reaches an inconsistent state mid-install (e.g. a previously-aborted Phase 6 run left a partially-written Path A while Path B was still present).
  - **`Invoke-DpkgQueryNative` seam** (`Sync-MicrosoftAptSource.ps1:75-119`) -- new module-private wrapper that pins `LC_ALL='C'` for stable English stderr matching, restores it in `finally`, and returns `{ExitCode, Output, StdErr}`. Shared by the conflict scanner and the cleanup helper so tests mock one function instead of forking `dpkg-query`. No `pwsh` subprocesses in any new test (PowerShell-test performance and correctness rule).

## [0.54] - 2026-05-17
- **Goal**: Harden MCP install resilience in `vibeshield-bicep` so the installer actually self-repairs the failure modes a user hit on a fresh machine: `dotnet tool update -g azure.mcp` failed with `Failed to create shell shim for tool 'azure.mcp': Command 'azmcp' conflicts with an existing command from another tool` even though `dotnet tool list -g` showed neither MCP package installed (orphan shims left in `~/.dotnet/tools/` after `.store/<pkg>` was wiped), and a separate run with a stale ADO feed in `nuget.config` produced a wall of `[NuGet Manager] [Info] [CredentialProvider]` chatter that buried the actually-actionable `Unable to load the service index for source <url>` line. C1 closes ADO bug [525807](https://dev.azure.com/oneCELA/CELA%20Engineering/_workitems/edit/525807/) by adding a new repair arm for the orphan-shim case AND patching the existing `DotnetToolSettings.xml` deep-clean path so it stops manufacturing that exact state (the deep-clean discards `dotnet tool uninstall`'s exit code and then wipes `.store` + `~/.nuget/packages` without touching the shim files, so a silent uninstall failure leaves shims orphaned -- a fix that only added the new arm would repair on top of a code path that re-creates the bug on the next run). C2 closes bug [525806](https://dev.azure.com/oneCELA/CELA%20Engineering/_workitems/edit/525806/) by classifying every `dotnet tool` failure into one of five categories, stripping credential-provider chatter from user-facing output, and writing the full raw output to a sidecar log so diagnostics stay reachable without dominating the terminal.
- **What** (C1): all changes in `skills/vibeshield-bicep/scripts/Install-McpConfig.ps1` and its test file `.vibeshield/AgentTests/vibeshield-bicep/Install-McpConfig.Tests.ps1`.
  - **Repair surface widened from one signal to two.** A parallel arm in `Invoke-DotNetToolAction` now matches `(?i)conflicts with an existing command from another tool` (alongside the existing `DotnetToolSettings.xml` arm) and performs whitelist shim-file deletion under `~/.dotnet/tools/` (canonical extensions only -- `.exe`/`.cmd`/`.ps1` on Windows, no-extension on Unix), then runs the existing `.store` + `~/.nuget/packages` cleanup, then retries the install once. On clean repair the user sees `REPAIRED`; on retry-fail the warning names the retry exit code, the shim command, and the manual paths.
  - **Self-repair must not manufacture the state it repairs.** The existing `DotnetToolSettings.xml` deep-clean discards `dotnet tool uninstall`'s exit code (line 274) and then wipes `.store/<pkg>` + `~/.nuget/packages/<pkg>` without touching the shim files under `~/.dotnet/tools/` -- on a silent uninstall failure the shims are left orphaned, exactly the state the new conflicts arm has to clean up. The deep-clean arm now also runs the same defensive shim-file cleanup, so future repairs cannot recreate this bug on the next run.
  - **Two callers, two severity contracts.** A safety-check refusal (a shim claimed by a *different* registered tool, or `dotnet tool list -g` cannot be queried at all) is *terminal* in the conflicts arm because retry would reproduce the same conflict; the same refusal in the defensive deep-clean arm is *advisory* because the original failure was not shim-related and retry can still succeed. The shim-cleanup helper therefore returns structured data and lets each caller decide whether to escalate to `$script:McpInstallFailures` -- it never mutates installer state on its own. Distinct `ABORTED` vs. `SKIPPED` message verbs make the path visible in logs.
  - **Fail-closed safety.** Never delete a shim we cannot prove is unowned. If `dotnet tool list -g` throws or returns a malformed listing, the helper refuses with an `<unverifiable>` sentinel in the user-facing message rather than deleting on optimism. The list parser is also localization-safe (skips header rows by SemVer-shape check on column 2, not by English `Package Id` string match) and multi-command-aware (a tool whose Commands column is `azmcp, othercmd` is correctly identified as the owner regardless of which position the target command occupies).
  - **Test isolation regression averted.** The defensive shim-cleanup added to the DotnetToolSettings arm fires from pre-existing tests #16/#17/#18/#22, whose `dotnet tool list -g` mock returns empty (safety check passes → cleanup runs). Without intervention these tests would delete the developer's real `~/.dotnet/tools/{azmcp,Azure.Bicep.McpServer}.{exe,cmd,ps1}` shims on every run. The `$env:USERPROFILE = "$TestDrive\fake-home"` redirect is hoisted to file-level `BeforeEach`/`AfterEach` so every test inherits it by default and no future test can re-introduce the leak.
  - **Tests** -- new `Context 'Orphan shim repair (ADO #525807)'` with 10 `It` blocks (#23-#32); file total 32 (up from 22). Coverage includes the happy path with real planted shims, cross-tool safety refusal with cache-survival assertions, the self-manufactured-state path through the DotnetToolSettings arm, localized-header parsing, multi-command-owner first-in-list detection, fail-closed on `dotnet tool list -g` non-zero exit, and `<unverifiable>` + multi-command remediation rendering.
  - **`version.json`** bumped 0.53 -> 0.54.
- **What** (C2): all changes in the same script + test file as C1.
  - **Dispatch by failure category, not by inline regex match.** Failure paths used to be a chain of `if ($outputText -match '...') {...}` checks at each emission site. A single classification step at the boundary of every failure handler now returns one of five categories (`ServiceIndexUnreachable`, `Conflicts`, `DotnetToolSettingsMissing`, `TfmMismatch`, `Unknown`) plus a one-line summary, an actionable remediation hint, and category-specific captured tokens (URL for ServiceIndex, conflicting command for Conflicts, required SDK major for TfmMismatch). Pattern order is most-specific-signal-first so multi-match text classifies correctly. The classifier is a pure function (no `Write-Host`, no disk I/O, no mutation of installer state); every callsite decides how to react. The `Unknown` fallback distills to the last 3 non-empty non-chatter lines (newline-joined) so users still see the real dotnet error even when the pattern is unrecognized.
  - **`TfmMismatch` gets its own short-circuit arm.** Previously TFM failures fell through to the `DotnetToolSettings.xml` deep-clean (both surfaces mention `DotnetToolSettings.xml`), which can never recover from a TFM mismatch -- reinstall pulls back the same `net<N>.0` assets and fails identically. The classifier captures the *actual* required SDK major from the error text (e.g. `12` when the package targets `net12.0`) and the dedicated arm surfaces "Install .NET SDK 12" even when the config-derived `$requiredSdkMajor` only knows about `net10.0`. The in-arm SDK preflight inside the DotnetToolSettings arm remains the disambiguator for the ambiguous `DotnetToolSettings.xml` + SDK-too-old surface that cannot be told apart from genuine cache corruption from surface text alone.
  - **Separate the raw diagnostic from the user-facing message.** Every classified failure now writes its full raw `dotnet` output (including credential-provider chatter, for diagnostics) to a sidecar log at `output/mcp-install-<pkg>-<timestamp>-<hex>.log` (timestamp + 4-char GUID-derived suffix to prevent same-millisecond collisions). The user-facing WARNING and the entry pushed to `$script:McpInstallFailures` become a one-line per-category summary + remediation hint + log path; credential-provider chatter never reaches the terminal but is reachable on demand. Lazy directory creation so successful runs leave no artifact under `output/`. Sidecar-write failures are non-fatal but the fallback message stays truthful -- the raw output is also `Write-Verbose`'d unconditionally so `-Verbose` callers can recover it even when the disk write fails. The sidecar writer returns `$null` under `-WhatIf` so callers do not reference a file that does not exist.
  - **Apply the new shape to every failure path, including repair-arm retry failures.** The C1 repair arms originally still emitted raw `$retryText` on retry failure, so a machine with both an orphan shim AND an unreachable feed (empirically the original bug-525806 repro) would still see the chatter-dominated WARNING this bug is about. Both repair arms now classify `$retryText` and reuse the sidecar-log pattern. The C1 manual-remediation hint stays appended *only* when the retry's category differs from the original arm's category; same-category retries suppress the duplicate hint because the classifier output is authoritative there.
  - **Strip credential-provider chatter from user-facing output, preserve everything else.** A `FilteredOutput` field removes lines matching `^\s*\[NuGet Manager\]\s*\[Info\]\s*\[CredentialProvider\]`. Non-prefixed content -- including the actually-actionable `Unable to load the service index ...` line and any line that merely mentions "CredentialProvider" in passing -- is preserved verbatim. The `Conflicts` remediation hint substitutes the captured command name into the message (e.g. `'azmcp.exe'`, `'azmcp.cmd'`, `'azmcp.ps1'`) so users get copy-pasteable instructions instead of literal `<cmd>` placeholders.
  - **Make the PS7 dependency explicit.** This entry added the first uses of `??` to the script. Without `#requires -Version 7.0` it silently fails to load under Windows PowerShell 5.1, taking the C1 orphan-shim repair down with it. Added `#requires -Version 7.0` to both script and test files.
  - **Tests** -- new `Context 'Failure classifier (ADO #525806)'` with 16 added `It` blocks (SC1-SC15 + SC-meta); file total 48 (up from 32). Coverage includes per-category classification of the bug-report verbatim text, the rubric-pass gate asserting no `[CredentialProvider]` substring reaches `Write-Host` for ServiceIndexUnreachable, end-to-end sidecar-log writing under `output/` containing the full chatter-included raw output, regression-protection for the consolidation (DotnetToolSettings.xml dispatch and Conflicts dispatch still reach their existing repair logic), repair-arm retry-fail chatter filtering for both arms, TfmMismatch short-circuit asserting the captured `RequiredMajor` reaches the WARNING and no deep-clean fires, and `-WhatIf` returning `$null`. Two pre-existing tests (#15 and #19) updated to assert the new consolidated message shape without weakening the original intent (test 19 still asserts pure service-index failures do NOT trigger DotnetToolSettings repair). An `SC-meta` test pins a PowerShell wildcard-semantics gotcha discovered during review -- `$Object -like '*[NuGet Manager] [Info] [CredentialProvider]*'` matches nothing because PowerShell treats `[...]` as a character class, not literal brackets; the previous negative assertions were vacuously true, replaced with `.Contains()`, and the meta-test asserts both that the broken pattern returns false and the fixed pattern returns true on real chatter.

### Security

Blocks all shell metacharacters: `;` `|` `&` `$` `` ` `` `<` `>` `(` `)` `{` `}` `!` and quotes.
  - Added `$staleOpenEndedMarker` detection to auto-replace old open-ended entries on re-install.
